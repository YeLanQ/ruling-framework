# 01 · 原理：把裁定权从模型侧拿走

## 1. 一个统一解释

智能体系统反复出现的四类结构性缺陷：

1. **经验复用失效**：已解决的问题换个说法就重新推理。
2. **执行过程黑盒**：结果不可归因，失败只能重试。
3. **行动边界缺失**：能力所及即执行，副作用无法提前拦截。
4. **运行成本失控**：全库检索、全量重嵌入、微调再训练。

本框架采用一个配置结构假说：四类缺陷的共同根源是**验证、执行、放行三类裁定的最终权威滞留在模型侧**。

- 经验复用失效，因为检索与记忆只对推理有建议效力；
- 执行黑盒，因为验证结论由执行者自评；
- 边界缺失，因为授权与执行同源于模型决策；
- 成本失控，因为系统用“更大的辅助”补偿“更弱的限定”。

这是关于**配置结构**的假说，不是已被实验隔离的因果定律。它带来的工程立场是：可靠性的改进对象不是模型推理能力，而是裁定权的配置结构。

## 2. 三权外置

| 裁定 | 归属 | 在本框架中的落点 |
| --- | --- | --- |
| 验证裁定 | 机器门禁 | 单元测试、类型检查、审计校验、格式校验；不是模型自评 |
| 执行裁定 | 唯一命令中心 | `RulingEngine.execute` → `ActionExecutor`，无旁路 |
| 放行裁定 | 用户源头授权 | pack 的角色能力组 + 运行态审批会话 |
| 知识裁定 | 大脑前置 | `engine.prepare` 决定模型看到哪些决策单元 |
| 决策空间裁定 | 决策单元锁定 | 动作表封闭、候选动作由前置路由给出 |

本框架实现前四项；第五项以“能力面 + 候选动作”形式落地，不引入持久化的模因对象。

## 3. 四个机制

### 3.1 大脑前置

在模型主推理趟之前完成：

- 规则分段；
- 知识路由（哈希嵌入 + 图谱邻接 + 类型先验）；
- 候选动作预测（关键词 / 知识 `uses` 边）；
- 单元分流：唯一高置信度绿灯动作直接执行，完全不经过 LLM。

模型收到的不是“可能相关的知识集合”，而是“已经确定的决策单元与候选动作”。

### 3.2 决策单元锁定

一次推理被绑定到一个动作表内的决策单元：

- 动作 id 是稳定契约；
- 动作表封闭，表外动作不存在；
- 锁定的是单元，不是表述；换一种说法仍然落在同一动作表内。

### 3.3 原子命令中心

“原子”指**单一、不可绕过的入口**，不是 ACID：

- CLI、HTTP、MCP、Agent 循环全部调用 `RulingEngine.execute`；
- 执行器只能通过引擎提供的工作区访问文件；
- 没有“模型直接改状态”的第二条路。

### 3.4 知识-权限生命周期分离

- 知识跨会话持久：seed / extended / error、图谱、台账、因果链。
- 权限仅运行态：审批会话是内存哈希表，TTL 过期，不写快照，不跨进程。
- 两套状态空间只在“用户批准 → 命令中心执行”处交汇。

持久化权限必然腐化：授予语境消失后权限仍然存续。运行态权限的代价是每次会话重新放行，这是本框架愿意支付的成本。

## 4. 行动三区

| 区域 | 判定 | 行为 |
| --- | --- | --- |
| 绿灯 | 只读、无副作用 | 直接执行 |
| 黄灯 | 写操作、共享状态、不可逆但可批准 | 需任务级批准 |
| 红灯 | 规则上禁止 | 拒绝，即使批准也不放行 |
| 未登记 | 不在能力表内 | 永远不执行；agent 路径返回 needConfirm |

### 4.1 门控真值表

```ts
gate(zone, approved, known):
  red                          -> deny
  green                        -> autoExecute
  yellow + approved + known    -> autoExecute
  yellow + 其他                -> needConfirm
```

三个细节：

1. `known=false` 时即使 `approved=true` 也返回 `needConfirm`。系统对未登记动作没有边界证据，宁可多问。
2. 红灯在角色授权之前判定为 `RED_LINE`，保证“绝对禁止”不被角色差异掩盖。
3. 动态红灯（工业设计安全参数）在区域解析阶段升级，仍走同一 `gate`。

### 4.2 审批语义

- 键是任务文本，截断 200 字；
- 默认 TTL 10 分钟（工业设计包 15 分钟）；
- 只存内存，不写快照，不跨进程；
- 小公司可按能力组要求多个不同角色；
- 同一角色重复批准不计数；
- 批准只实例化源头策略，绝不扩大它：未登记动作即使批准也不执行。

### 4.3 批准不是模型工具

模型只能收到 `needConfirm`。批准只能来自：

- CLI 的 `--yes`（人的显式动作）；
- HTTP `POST /approve`（对同一运行进程）；
- 宿主应用自己实现的人机确认回调。

MCP 工具列表里没有 approve，避免模型自我批准。

## 5. 效能门不是安全门

效能比：

```text
accuracy = (successes + 40 * 0.995) / (attempts + 40)
speed    = min(1, speedBudgetMs / avgMs)
energy   = min(1, 5 / (avgMs/1000 * energyWeight))
ratio    = accuracy * (0.5 * speed + 0.5 * energy)
```

- 冷启动 ratio ≈ 0.995；
- 20 次执行 1 次失败，ratio = 0.98，低于 0.99；
- 0.99 只用于**计划级建议**：是否值得不再打扰用户；
- 单次黄灯写操作永远不会因为历史 ratio 高而放行。

把性能指标当权限模型，是这类系统最常见的误读。

## 6. 信任模式

框架显式区分两条路径：

| 能力 | `agent`（内置自主 Agent） | `operator`（用户主动接入的自动化） |
| --- | --- | --- |
| 能力面封闭 | 是 | 是 |
| 源头角色授权 | 是 | 是 |
| 三区逐动作批准 | 是 | 否 |
| 红灯阻断 | 是 | 是 |
| 数据边界/格式锁 | 是 | 是 |
| 输入 schema | 是 | 是 |
| 审计 | 是 | 是 |

`operator` 不是“更安全”，只是信任模型不同：用户已经通过启用服务、配置角色表达了授权，再对每个写操作弹批准会让 CI/脚本无法工作。对不完全可信的 Agent，正确做法是只授予必要能力组，而不是指望提示词约束。

## 7. 伴随式定位

本框架不追求任务泛化率，而以过程可控性为先决条件：

- **在场性**：知识域限定于当前工作区/项目。
- **可见性**：每个执行单元的区域、决策、原因、结果可观测。
- **最小权限**：执行许可由用户在源头授予。
- **成本可控**：知识更新按层递减，不做全量重嵌入或参数级更新。

可靠性由工程供给，智力由模型供给。模型可以替换，约束不随供应商改变。
